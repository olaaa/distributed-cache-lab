| № | Сценарий | Вопрос сценария | Тест | Статус |
|---|---|---|---|---|
| 1 | [`RedisCacheManager` и сериализация](01-redis-cache-manager.md) | как перенести `@Cacheable` в Redis и что сломается с настройками по умолчанию | `Scenario1RedisCacheManagerTest` | готов |
| 2 | TTL с разбросом | как не дать записям, загруженным одновременно, одновременно и истечь | — | планируется |
| 3 | Двухуровневый кэш: Caffeine плюс Redis | как не ходить в Redis по сети за каждым чтением | — | планируется |
| 4 | Инвалидация локальных кэшей между репликами | как сообщить остальным репликам, что их локальная копия устарела | — | планируется |
| 5 | Удаление после коммита и гонка в Redis | почему удаление после коммита не спасает от старого значения в Redis и что с этим делать | — | планируется |
| 6 | Лавина промахов и `@Cacheable(sync = true)` с Redis | объединяет ли `sync = true` одновременные промахи, когда кэш — Redis | — | планируется |

Порядок может поменяться: сценарии делаются по одному, следующий — после разбора предыдущего. Номер 6 — проверка предположения из сценария 1: по исходнику `RedisCache.retrieve(key, valueLoader)` читает и пишет без блокировки, значит `sync = true` одновременные промахи, вероятно, не объединяет.

## Общее для всех сценариев

- Источник — `ProductSource`: читает БД с задержкой 50 мс (в тестах 100 мс), считает обращения и умеет падать. Главная проверка каждого теста — `source.callCount()`.
- Перед каждым тестом `ScenarioTestSupport` очищает таблицу, вставляет «Чайник» (id 1, 2490.00), очищает базу Redis и сбрасывает счётчик.
- Посмотреть, что лежит в Redis, тест может напрямую, через `ReactiveStringRedisTemplate`, а вручную — через `docker compose exec redis redis-cli`.
